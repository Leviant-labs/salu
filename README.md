# Salu

Local-first nutrition app: logging, meal planning, coaching and supportive
tracking, with AI as an *optional interaction layer* over a deterministic core.
Flutter for iOS and Android. Records live in SQLite on the device; there is no
account and no backend.

Spec: [`docs/product-spec.md`](docs/product-spec.md) (product contract and
release gates) and [`docs/nutrition-engine-spec.md`](docs/nutrition-engine-spec.md)
(calculation mechanics).

## Layout

```text
app/                    Flutter app: UI, composition root, platform adapters
packages/salu_core/     Pure Dart: domain, nutrition math, typed commands, ports
packages/salu_data/     Drift/SQLite: schema, migrations, repository adapters
docs/                   Spec, architecture, decisions
tool/                   Repo-level checks
```

Dependency direction is one-way: `app` → `salu_data` → `salu_core`, and
`salu_core` depends on nothing but the Dart SDK. `tool/check_boundaries.sh`
fails the build if that is violated.

## Run it

```bash
# 1. codegen: drift tables -> app_database.g.dart (not committed)
cd packages/salu_data && dart pub get && dart run build_runner build

# 2. packages
cd packages/salu_core && dart pub get && dart analyze && dart test
cd packages/salu_data && dart analyze && dart test

# 3. app: platform folders (android/, ios/) are generated, not committed
cd app && bash tool/bootstrap_platforms.sh
flutter pub get && flutter analyze && flutter test
```

`packages/salu_data` needs a sqlite3 shared library on the host
(`libsqlite3-dev` on Debian/Ubuntu).

## What actually works

- Domain model with nutrient values that distinguish **unknown / measured zero /
  trace / estimated**, and arithmetic that never converts unknown into zero.
- Diary time semantics: instant + recorded UTC offset + assigned diary date, with
  an optional day-boundary hour.
- Quantity resolution to grams; volume and piece counts only convert when the
  food declares a density or a portion weight, otherwise the command is rejected
  with a recoverable message.
- One typed write path end to end: `LogFoodHandler` → `LogFoodCommand` →
  SQLite, idempotent on `requestId`, snapshotting nutrients so catalogue updates
  never rewrite history.
- Drift schema v1 with foreign keys, a unique request-id index, and tests
  covering round trip, idempotency, cascade delete and snapshot stability.
- App shell: four tabs (Today, Food, Plan, Settings), live diary for today,
  catalogue search with a one-tap 100 g log, and an empty-state plan tab.

## What is deliberately absent

Stubs and placeholders are labelled as such in the UI:

- Meal planning, coaching, targets, adaptive expenditure, grocery lists.
- Barcode scanning, label OCR, meal-photo drafts, natural-language logging.
- Inference providers, health exchange, export/backup, gamification.
- Localisation (EN + pt-PT) and accessibility pass.
- `android/` and `ios/` host projects — generated by
  `app/tool/bootstrap_platforms.sh` on a machine with the Flutter SDK.

Nothing in the tree claims an unmeasured capability: fixtures are tagged
`dev-fixture` and no imported record is labelled verified.
